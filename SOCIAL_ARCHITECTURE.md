# StayGrubby social architecture

Profile-photo/sharing-default enhancements are implemented and deployed: 18 aligned migrations, three private photo buckets and avatar-aware delete-account v4. Verification and remaining physical/privacy release actions are recorded in [SOCIAL_UX_REVIEW.md](SOCIAL_UX_REVIEW.md).

Private cooking history and the social graph are separate. Social APIs never return the CookingGraph, private media paths, Auth identities, email or sync metadata. Social engagement never changes comparisons, strengths, scores, personal ranks or score-unlock eligibility. Existing accounts may keep using private StayGrubby without social setup.

## Identity

Reuse the permanent account and existing profiles table. Display names collapse whitespace, allow nicknames and have a 50-character limit. Usernames trim whitespace/one optional leading @, lowercase, and require 3–24 ASCII letters/numbers with single internal underscores. The existing case-insensitive unique index is authoritative. A small deterministic platform/system-name set is reserved, including underscore variants. Old handles are reserved to their account for 30 days after rename; the same account may reclaim them. Account deletion cascades reservations. No redirects or marketplace.

Discoverability defaults false. Setup is optional; identity edits use an authenticated owner-derived RPC, with no direct client writes. Discoverability controls normal search, not existing friendship identity or private cooking. Optional profile photos are implemented below; bios are not implemented. Social responses are held in the account-mounted UI, never hydrated into private cooking stores. Account-generation checks discard stale replies after switching/sign-out.

## Verification policy

Compile and focused feature tests at each checkpoint, one Simulator lane. SQL tests use disposable PGlite Auth/session stubs, not real Apple authorization. Hosted checks compare version/name/hash, grants, RLS and non-sensitive private-data fingerprints before/after each migration. Real Apple deletion, physical device tests, full historical ranking/photo/sharing/Cuisine suites and release builds are excluded unless a concrete dependency demands them.

## Mutual friendship and blocks

One canonical unordered UUID pair row holds requester and pending/friends/declined/cancelled/removed state. Pair-scoped transaction locks serialize transitions; live Auth/account checks repeat after lock waits. Same-direction requests are idempotent; crossed eligible requests become friends. Only recipients accept/decline, only senders cancel, either friend removes. A declined sender waits 24 hours before retry; the recipient may initiate a new request. Stale transitions fail with refreshable conflict status.

Directed blocks are a separate private security primitive. Either-direction block suppresses normal social lookup/requests and retires pending/friend state. Only the blocker can remove their block; unblock restores nothing. The blocker's own blocked list may identify users they deliberately blocked. Friendships/blocks/reservations cascade with permanent account deletion. Clients have no direct table writes or raw social-table reads; narrow owner-derived RPCs return minimal social DTOs. Search is username-only, requires 2–50 characters, excludes self, respects discoverability and blocks, and uses 50-row username cursors. Existing friends/requests retain identity access when discoverability is off. Internal peer IDs are opaque action references and are never displayed as profile content.

## Friends UI

Friends is reached from Profile and the Friends Feed toolbar; Rankings remains the default tab. Native lists provide friends, incoming requests, outgoing requests, username search and the caller's blocked list. Search is debounced, keyboard-friendly and excludes undiscoverable/blocked people. Username cursors bound normal lists to 50 rows per response with Load more. Minimal person sheets expose only name, @username, relationship and permitted actions; no private cooking graph, Top 3, email, raw account identifier, allergens or sync metadata. Remove/block use confirmations. Server refresh is authoritative after mutations/stale conflicts; errors clear stale list content and permit retry. Social setup remains optional and does not gate private cooking.

## Safety and content privacy

Friends-only post visibility is enforced in private SQL: author/current eligible friends only, with active accounts/profiles, published/unretired/unhidden content and either-direction blocks applied. Discoverability is independent of existing friendships/content access. No raw social-table grants are provided to clients; every new table has RLS. Profiles/comments/posts have service-controlled active/hidden states. Hidden social identities cannot interact socially but retain private cooking access. The service-only moderation RPC cannot be called by authenticated or anonymous clients. Protected operators can review pending reports in SQL; no admin dashboard, external vendor or AI moderator is added. Operational response procedures remain an owner responsibility before broader distribution.

Reports target a currently accessible profile/post/comment, use six reasons and optional 500-character context, deduplicate by reporter/target, and cap new reports to 50/day. Clients receive only reported=true; targets cannot read raw reporter/context data. Reports do not automatically hide content. Reporter/target-account and post/comment foreign keys provide deletion cleanup without a new retention archive. Profile reporting is available before blocking; inaccessible targets cannot be used to infer private data. Native report UI uses the same boundary. Existing inaccessible-table INFO advisor notices are intentional; see https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy. The pre-existing disabled-password warning is unchanged: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection.

## Explicit cooking snapshots and social photos

Cooking stays private. Share with Friends is separate from native image export and requires explicit confirmation; optional photo consent defaults off. A server snapshot derives title, version and legitimately unlocked score from the authenticated author's synced cook and revision. It never trusts client authorship or score and never writes ranking evidence/caches. One active snapshot per cook prevents retry duplicates. Existing snapshots do not track private edits/re-ranking; delete/re-share to update. Deleting the source cook retires its social snapshot. Deleting a social post never deletes its private source.

Only share-safe snapshot fields leave the social API. Photos are copied only on explicit consent into the separate private `social-photos` bucket at author/post.jpg. Registered drafts accept owner-only JPEG uploads; publish verifies the object exists. Current friendship/block/moderation checks gate reads; the cooking-photos bucket is unchanged. Retired photos become inaccessible immediately and cleanup retries on social refresh. Account deletion now removes all three photo buckets before graph/Auth erasure; deployed delete-account v4 preserves the existing Apple proof/revocation flow. No real account deletion was performed.

## Chronological Feed

Feed is a bounded friends-only snapshot timeline, newest publication time first with UUID tie-breaker. Pages contain at most 25 posts and use an exclusive `(created_at,id)` cursor; no offset, popularity ranking or recommendation system. `api.social_feed` exposes page and individual visible-post reads only. Discovery off does not remove existing friend access. Retirement, moderation, account deletion/deleting state, block and removed friendship are enforced on every server read.

The default tab remains Rankings; Feed and Profile complete the navigation. Pull-to-refresh, returning to foreground, returning from profile safety actions and local social changes reload server truth. Visible content clears on background/tab exit and on refresh errors, avoiding indefinite offline reuse of revoked social content. There is no real-time/push revocation; another person's changes are reflected on the next request/refresh. Already seen/downloaded content cannot be remotely recalled. Shared by me provides draft/hidden status and confirmed post deletion without touching private cooks. Cards use authenticated social photos/fallback, semantic native score colors, minimal profiles and reporting.

## Likes and flat comments

`api.social_interactions` derives the actor from the live authenticated account; no client-supplied author/liker is accepted. One primary-keyed like per account/post makes like/unlike idempotent. Flat comments normalize whitespace, allow 1–1000 characters and enforce a 60-per-hour actor cap. Stable caller comment UUIDs make unchanged retries idempotent. Deleted comments keep an ID tombstone with cleared body, preventing delayed retries from resurrecting text. Comment author and post owner may delete; no other participant can. Reports of deleted/hidden/ineligible comments are denied.

Parent visibility is mandatory for all reads/writes. Participants must still have parent-post access; blocked pairs cannot see each other through a third friend's post. Visible counts may therefore differ by viewer and exclude hidden/deleted/blocked/ineligible participants. Counts are returned in the existing page/card request, with indexed per-post aggregates; no per-card network round trips for counts. Comment pages use exclusive timestamp/UUID cursors, newest first, at most 25. Participation intentionally shares only minimal social identity, text and timestamp; an undiscoverable participant's comment does not expose private cooking data. Relationship changes can hide old engagement; re-friending can restore still-retained engagement. Account/post erasure cascades likes/comments/reports. Engagement never touches ranking calculations, evidence, unlock state or private sync revisions.

## Integration and release boundaries

Child report/composer sheets retain their owning rows while presenting; disappearing for a child modal invalidates pending loads without deleting the sheet anchor. Background and actual Feed-tab exit still clear social content. Parent-owned presentation bindings close composer/report sheets explicitly. Confirmation visibility is independent of selected data and uses SwiftUI's presenting-data API. Comment deletion is queued in local state and executed by the mounted screen's task, so a dismissing dialog cannot refresh a detached captured view. These are social UI lifecycle corrections, with no private cooking/navigation redesign.

The bundled canonical policy now describes optional identity/discovery, explicit friend-only snapshots/photos, visible participation, report privacy and deletion. Website generation uses that exact policy; publishing the website and reviewing App Store privacy for the new social practices remain owner release actions. No new TestFlight build, Apple configuration, archive or physical Apple deletion is part of this run. Actual signed-in two-account/device and real social JPEG transport review is recommended before broader distribution; local security tests emulate Auth/Storage catalog boundaries and do not claim live HTTP/Apple authorization or remote photo-byte testing.

Public StayGrubby profile links, `staygrubby.com/@username`, Universal Links and QR profile sharing are intentionally deferred. Optional social identity does not create a public website/profile or grant access to private cooking.

## Optional profile photos

Social identity photos use the separate private `profile-photos` bucket, never `cooking-photos` or `social-photos`. Version paths are `<permanent-account UUID>/<asset UUID>.jpg`. Native PhotosPicker passes only the selected image to an in-memory ImageIO downsample/re-encode (maximum 360px, stripped metadata); the UI crops to a circle without cropping the stored image. Bucket limits are JPEG/2 MiB; the client validates complete JPEG bytes/dimensions. No public/signed avatar URLs or disk avatar cache are created.

An owner-derived avatar RPC reserves a draft, validates uploaded object metadata before publishing and retires the former version. Upload/upsert is allowed only to that account's registered draft. Reads require live authentication, an active social identity and permitted social visibility (self, discoverability, friendship/request or visible post/comment participation), with authoritative blocks. Arbitrary bucket listing is denied. A removed/replaced path immediately loses read access; an unfinished draft expires during profile cleanup after a day of profile inactivity; bounded owner-only cleanup retries on profile changes/visits, and coordinated account deletion clears/verifies all three buckets before graph/Auth erasure. The screen and account-session generation discard stale/cancelled photo replies. Initials (or a restrained fork/knife mark) provide the fallback; visible names/handles remain the identity.

## Sharing defaults

`profiles.auto_share_new_cooks` is a server-owned account preference, default false for every legacy/unset account. Identity setup explicitly offers Automatically Share New Dishes; a configured social identity does not require opting in. Profile → Social settings changes the preference through the authenticated owner-derived identity RPC. This is not device UserDefaults. Other clients fetch it for the account; unknown/unavailable defaults remain private. Old clients that omit the preference preserve an existing explicit choice. Changing it only affects future creation defaults and never publishes, removes or rewrites cooking history or existing posts.

## Per-entry choice and completed-cook outbox

New Dish and New Version load the current account preference and allow a per-entry Share with Friends override. A late preference reply cannot override the user's choice, and Continue freezes the displayed choice (unknown defaults OFF) before ranking. Edit, re-rank and restoration do not call the creation-only intent hook.

The account-root `SocialPublicationOutbox.json` is a separate local publication journal, not a CookingAttempt/RankedItem field or private sync graph change. It contains only account/item/post identifiers, photo consent, timestamp and whether scores were locked. Intent is saved before the new private transaction using the newly allocated RankedItem UUID. No post is created until a matching saved cook exists and its structured sync is ready. The root worker survives modal dismissal, retries on foreground/sync progress and exposes Retry/Keep private in the result and Profile pending shares. Its owner-validated journal survives relaunch; it is not cloud-restored, so restoring cooking alone never creates publication intent. Unfinished/cancelled forms with no saved matching cook cannot publish.

Manual composition and this outbox share one `SocialPostPublisher`, the existing social_content API, one-active-post-per-cook constraint and separate social-photo upload. Stable post IDs and persisted canonical IDs make retries idempotent; a deleted post ID is not silently resurrected. A social/API/photo/journal failure does not roll back or duplicate private cooking/ranking. Publication may finish before the result or remain explicitly pending while sync/network work completes. Snapshot fields come from the server's accepted private revision; hydration leases need not block publication once structured mutations are acknowledged. Private photo-byte backup is independent of the separately authorized social copy.

Scores remain server-gated and snapshots remain immutable. The journal records the actual saved cook's existing unlock state, not a new numerical threshold. If an entry was locked when saved but scores unlock before its pending publication, automatic publication pauses for explicit review through the existing composer. This does not update already-shared locked snapshots or automatically disclose historical scores. The journal contains no score, strength, comparison, notes, tag or private-photo URL. Changing defaults never changes existing intents/posts; users can cancel a pending share explicitly. Native image-card Share/Save Image is unchanged and does not create a social post.


## Shared Cooking, Recreated and in-app notifications

The new phase is documented in [SHARED_SOCIAL_REVIEW.md](SHARED_SOCIAL_REVIEW.md). Private cooking → personal ranking → optional controlled social representation → interaction remains the boundary. Four purpose-specific closed/RLS tables represent stable UUID events, independent participant decisions, recipient-owned origin claims and canonical notifications. The owner may invite up to eight current friends after saving/ranking; no participant receives a private entry automatically. Joining/Make This opens an editable new-cook form using a durable server-reserved personal item UUID. Normal CookingStore and the unchanged ranking engine create the recipient's own attempt/item/evidence. Retried claims reuse the item, and completed/locally saved entries route to the existing cook instead of creating another.

Safe shared metadata is title/Course/Cuisine and public cookbook, restaurant or online attribution. New social posts require explicit includeAttribution consent from the updated app; older clients and existing snapshots do not gain metadata on retry. Friend/Family details, private notes, dietary/allergen annotations, URLs, comparison history, scores and private photo objects never prefill another library. Recreated source attribution remains distinct from the friend who cooked it. No photo copy/download infrastructure is added to joining; recipients choose their own photos. Existing controlled social-food and profile media remain separate from private cooking media.

A separate owner-bound SharedCookingOutbox.json, excluded from device backup, queues selected participants/origin completion before the private transaction. Only a matching saved cook and accepted structured sync can send it. Failure preserves private history; retry is idempotent and pending invitations can be cancelled explicitly, including after a lost reply. Completed-origin linkage can recover when a user explicitly reopens an already restored claim; cooking restore alone creates no new intent. Feed publication remains independently controlled by existing account/per-entry sharing preferences. Completed Cooked Together/Recreated presentation uses current permitted identities; it never implies shared ranking evidence.

Canonical friendship/like/comment/invitation/completion transitions generate notifications with no client actor/recipient override. The bell in Feed and Profile opens chronological pages, unread state, Mark All Read and authorized native destinations. Source-derived visibility filters every page/count/action; no private numerical score or unnecessary content snapshot is stored. Repeated likes/requests/retries deduplicate rather than multiply rows. There is no push, Realtime subscription or popularity ranking. Returning to foreground/refresh checks server truth; viewed content cannot be remotely recalled.

Pending invitations retire on friendship removal/block; declined/removed invitations do not silently reactivate after re-friending. Joined private cooks survive. Owner erasure cascades social events/participants; surviving recipients' origin references nullify, never their private cooking/evidence. Notifications cascade with actor/recipient deletion; stale targets remain inaccessible even if dedupe history is retained. The existing v4 deletion function's three-bucket guard/cleanup remains sufficient; no function/secret/Auth change or real deletion is needed.

Future public StayGrubby web links are routing/deep-link surfaces into the native app, not a public recipe/content website. Stable non-secret UUIDs and explicit provenance prepare for later resolution, but are not public permission grants. No Universal Link, Associated Domain, QR, public profile/post/recipe route or web Feed is implemented.
