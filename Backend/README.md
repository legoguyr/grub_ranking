# Private cloud schema foundation

The hosted StayGrubby project is `lgjxbpycphhsswxoncmz` (PostgreSQL 17). The initial and access-hardening migrations were applied on October 11, 2026 using authenticated Supabase MCP tooling. No privileged credential was requested or stored. See [setup and verification](../supabase/README.md) for exact versions, exposure, results and remaining integration work.

`supabase/migrations/` is the authoritative deployment history. `schema.sql` is a first-install reference that concatenates those migrations; the tests require parity. Never reapply the reference to an existing database or edit an applied migration. Create follow-up migrations using the supported CLI and update the reference alongside them.

The schema requires Supabase's `auth.users`, `auth.uid()` and client roles. Permanent StayGrubby account UUIDs remain separate from Auth identities. All cooking keys and foreign keys include the account owner. Sources preserve seven raw types and every nullable legacy field; Contains and legacy Free tags remain distinct. Cached scores are full-precision data, with no server ranking engine.

All 15 application tables have RLS. Authenticated clients have owner-only SELECT on 14 tables; private Auth links have neither policies nor client privileges. Explicit revocations deny anonymous access and all direct client writes, including RLS-bypassing TRUNCATE. Authenticated helper execution is limited to the fixed-search-path account resolver and trusted self-provisioning function. Only the security-invoker `api.provision_account()` wrapper is exposed; tables and private helpers remain unexposed.

Soft-deleted rows retain IDs, versions and deletion timestamps as tombstone evidence. Domain parent FKs use deferred NO ACTION; account erasure cascades the full graph, while Auth identity deletion cascades only its link. Atomic deletion/restoration rules, consistent tombstone snapshots, receipt processing and retry retention must be implemented and tested before enabling writes. Self-provisioning is now implemented; mutation, import and snapshot RPCs are still absent.

Minimal profiles are private/owner-only. Username uniqueness is prepared; username changes, old-handle history, reservations and recycling remain undecided.

## Phase 3C Part 1 provisioning

`20261012021032_account_provisioning.sql` and `20261012021504_provisioning_session_guard.sql` are applied to the hosted project. The latter preserves the former's history and moves live-session validation after lock acquisition. The parameterless API derives `auth.uid()`, requires a matching active `auth.sessions` row and non-anonymous/non-deleted Auth user, and acquires a transaction-scoped advisory lock for that identity. It atomically creates only accounts, protected Auth link and minimal profile, or returns the existing active account. No library, ranking, guest import or signup trigger is created. The response carries format version, authenticated user UUID, permanent account UUID, server revision and initialized/uninitialized library state. Deleting accounts are rejected.

The private security-definer implementation uses a fixed empty search path, fully qualified relations/functions and no caller-supplied identities, dynamic user SQL or broad write interface. It is owned by the migration's trusted database owner; authenticated clients have EXECUTE only, not direct table writes. The exposed wrapper is security invoker. No RLS policy or table write grant was added.

PostgREST uses the supported authenticator-role schema configuration, retaining public/graphql_public and adding only api. This override is maintained by migrations; changing the Dashboard exposed-schema setting alone will not replace it. staygrubby/auth remain private.

For genuine concurrent transactions, install a local PostgreSQL 17 test cluster, start it on a temporary Unix socket with no network listener, set PG_TEST_SOCKET to its `/private/tmp/staygrubby-...` socket directory (and PG_TEST_PORT if needed), then run `npm run test:concurrency` in Backend/tests. The script refuses remote connection settings and creates/drops only a uniquely named fixture database. Its 13 assertions include 20 blocked callers plus the holding transaction, lost-response retry, rollback and revocation while waiting. Test-driver pg 8.23.1 is pinned; temporary binary tooling @embedded-postgres/darwin-arm64 17.10.0-beta.17 was used for this validation but is not an app/repository dependency.
